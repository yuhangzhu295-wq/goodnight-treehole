## 一、 对标 1：Soul — 匿名社区与共鸣表达

### 1. 产品定位与参考范围
- **参考对象**：Soul App（官方移动端公开功能体系与产品信息架构）
- **核心定位**：基于心理状态与虚拟身份的内容分享与陌生人共鸣社区。

### 2. 核心功能及交互设计
- **瞬间/动态**：用户以虚拟化身发布生活心情与生活碎碎念，支持文字与图片；信息流按时间或话题展示。
- **互动机制**：点赞、抱抱、评论；互动以单条内容为载体，弱化个人持久粉丝沉淀。
- **私信门槛**：非互相关注或未破冰陌生人间禁止任意发私信，需发起请求。

### 3. 来源依据
- Soul 官网公开产品介绍及用户内容安全规范（https://www.soulapp.cn/）。

### 4. 晚安树洞当前实现状态对比
- **已实现**：
  - `Square.vue`：无头像、无固定公开个人主页的纯匿名信息流，支持按心情标签（全部、委屈、焦虑、失眠等）筛选，每条树洞支持点赞“抱抱”（hug）与发表回应。
  - `MoodCreate.vue`：极简输入板，默认私密，选择公开后需经过系统审核（`pending_review`）。
  - `PeerNetwork.vue`：基于相似经历标签推荐，双向签署同意后方可建立 1v1 会话。
- **存在的差距与反证修正**：
  - 目前 API 控制器仍提供 `sort=hot` 排序参数，虽然前端已弱化，但只要存在“热门”排序就存在社交货币化诱导倾向。
  - 公开抱抱计数会引发用户的攀比心理。

### 5. 值得借鉴的设计
- **低门槛情绪便签**：提供预设生活困扰标签（“工作”、“恋爱”、“失眠”等），帮助用户快速启动表达。
- **双向破冰许可**：必须经被倾诉方主动查看并同意后才可私聊，杜绝骚扰。

### 6. 不适合照搬的设计（严格禁止）
- **严禁引入粉丝数、点赞榜、热度排行与达人徽章**：杜绝社交货币化，保护夜间去成瘾与低心理压力。
- **严禁引入常态化公域个人主页与用户发帖历史列表**：防止跨帖子分析人肉出用户真实身份。
- **“抱抱”计数应仅作者本人可见或模糊化**：前端展示弱化为“有人给了一个温暖回抱”，不显示精确数字引发流量焦虑。

### 7. 技术实现方案
- 后端：PostgreSQL `Post` 表建立 `(status, reviewStatus, createdAt)` 复合索引；个人归档通过 `listUserPublicPosts` 下推 SQL 过滤。
- 前端：平铺流式排版，移除吉祥物与多层嵌套卡片，突出文字可读性。

### 8. 成本、性能与维护风险
- 索引开销小，无图床托管外链压力，维护成本低。

### 9. 隐私与安全风险
- **作者匿名穿透风险**：API 响应绝对禁止返回 `userId`、真实 IP 或跨帖持久设备唯一码。

### 10. 验收测试方法（L1-L5）
- **L2**：断言 `GET /api/v1/posts` 响应字段无任何 `userId`、`ip`；私密帖子及未审核帖子无法从广场接口查询。
- **L4**：验证双用户流程：用户 A 发布公开树洞，经审核后用户 B 在广场看到并点击抱抱。

## 二、 对标 2：Signal — 私密通信、双向屏蔽与证据保留平衡

### 1. 产品定位与参考范围
- **参考对象**：Signal Private Messenger（安全通信协议规范与客户端交互）
- **核心定位**：极简、高隐私控制与端到端不可追踪私密通信。

### 2. 核心功能及交互设计
- **消息撤回（Recall/Disappearing）**：发送方限时撤回，撤回后对端变为提示占位。
- **引用回复（Quoted Reply）**：针对某条特定上下文消息进行精准引用。
- **双向屏蔽（Block）**：屏蔽后通信完全单向静默截断，全站不可见。

### 3. 来源依据
- Signal Protocol 官方文档（https://signal.org/docs/）。

### 4. 晚安树洞当前实现状态对比
- **已实现**：
  - `PeerConversation.vue`：消息气泡、引用回复联动、2 分钟内消息撤回（双端变为“一条消息已撤回”）。
  - `PeerPersistenceService.recallMessage`：行级锁内比对数据库 `clock_timestamp()` 校验 120 秒，清除原文并清空媒体 URL 快照。
  - 双向屏蔽：一方点击屏蔽，会话即刻原子关闭（`reason: blocked`），并在数据库记录全局拦截。
- **反证审查修正的关键矛盾（撤回 vs 证据保全）**：
  - *矛盾点*：纯端到端通信的“彻底抹除”与树洞平台的“防骚扰/反虐待合规举报”存在冲突。如果骚扰者发完违规言论后在 2 分钟内撤回，受害者将无法取证。
  - *裁决方案*：**双轨分离制**。用户侧界面彻底抹除并替换为“一条消息已撤回”；但在服务端底层，撤回的消息内容在**7 天安全宽限期**内作为加密只读快照保留在安全审计库中，仅当该会话发生 `PeerReport` 举报时，安全沙盒按最小必要原则（被举报点前后 10 条）冻结脱敏证据；7 天无举报则由后台 Worker 执行物理级 `unlink/DELETE`。

### 5. 值得借鉴的设计
- **双向屏蔽的静默防激化机制**：一方屏蔽后，对方发消息只显示状态未送达或通用提示，不弹出“对方已将你拉黑”，防止现实中关系激化。

### 6. 不适合照搬的设计（严格禁止）
- **严禁虚假宣传 Signal 级 E2EE**：树洞涉及未成年人保护、自残自杀危机干预专线（120/12356）与涉暴举报，必须在法定义务下保留受严格 RBAC 和审计管控的平台密文存证。
- **严禁绑定手机通讯录**：Signal 以真实手机号为网络寻址基石，而树洞必须坚持随机生成的匿名会话凭证。

### 7. 技术实现方案
- 撤回机制：PostgreSQL 行锁原子更新，同步在内存及返回实体中将引用目标脱敏为“一条消息已撤回”。
- 举报留存：独立 `PeerReport` 表，与会话解耦，7 天滚动清理。

### 8. 成本、性能与维护风险
- 采用 PostgreSQL 事务行锁与 7 天自动淘汰逻辑，系统开销极低。

### 9. 隐私与安全风险
- **跨会话泄露**：撤回消息如果在其他消息的引用快照中未被遮罩，会导致原文被二次带出。已在 `peerMessageForUser` 增加全局引用回查遮罩。

### 10. 详细验收测试方法（L1-L5）
- **L2**：断言发送后 119 秒内可撤回，121 秒撤回抛出 400；断言非发送者撤回抛出 400；断言 A 撤回 M1 后，B 在增量与全量同步中看到的 M1 及所有引用 M1 的消息均为“一条消息已撤回”。

## 三、 对标 3：Telegram — 富媒体、表情包与增量同步体系

### 1. 产品定位与参考范围
- **参考对象**：Telegram Messenger（贴纸生态与移动端协议）
- **核心定位**：极速响应、丰富的微表情互动与出色的弱网同步能力。

### 2. 核心功能及交互设计
- **表情与贴纸抽屉**：Emoji、官方静态贴纸、个人收藏夹分类平滑切换。
- **增量游标同步**：客户端本地保存 `maxSeq`，重连或轮询时只请求 `afterSeq > N` 的增量包。
- **幂等防重重试**：客户端生成 `clientMsgId`，网络重传时服务端静默返回已有消息。

### 3. 权威来源依据
- Telegram MTProto 贴纸与消息同步规范（https://core.telegram.org/api/stickers）。

### 4. 晚安树洞当前实现状态对比
- **已实现**：
  - 内置 8 款高保真治愈系矢量贴纸（“暖心拥抱”、“递热茶”等），支持按用户收藏持久化。
  - `PeerConversation.vue` 实现 Emoji + 贴纸面板，串行增量轮询带 `?afterSeq=` 游标。
  - `sendPeerMessage` 严格实施贴纸白名单校验，仅限平台受控贴纸。
- **反证审查修正的关键点**：
  - *序号与去重持久化*：`seq` 必须从数据库中已有消息的 `MAX(seq)` 恢复，严禁每次重启从 0 开始导致增量同步过滤丢失新消息；去重必须检查会话已持久化记录中的 `(senderUserId, clientMsgId)`。

### 5. 值得借鉴的设计
- **治愈系微表情直达**：在夜间疲倦、难于敲字表达时，允许一键发送温暖陪伴贴纸。
- **端侧单调渲染**：消息按 `seq` 严格升序排列，解决弱网并发下消息乱序跳动。

### 6. 不适合照搬的设计（严格禁止）
- **严禁开放用户自由上传外部动图作为贴纸**：防范恶意用户在自定义图片中内嵌二维码、个人联系方式或违法敏感图像。
- **严禁引入万人公开频道或超大群聊**。

### 7. 技术实现方案
- 后端：`SocialMultimediaService` + 数据库已持久化消息扫描恢复最大 `seq`；贴纸收藏写入专用数据表或持久化存储。
- 前端：Vue 响应式增量合并，收到撤回墓碑事件时精准更新本地视图。

### 8. 成本、性能与维护风险
- 增量同步相比全量轮询节省 95% 以上带宽与序列化开销。

### 9. 隐私与安全风险
- **内联 SVG 注入风险**：严禁允许客户端直接传入任意 `data:image/svg+xml;` 字符串；必须通过 `stickerId` 在服务端查找可信预置 URL。

### 10. 详细验收测试方法（L1-L5）
- **L2**：断言任意伪造 SVG 贴纸被后端 400 拦截；断言重启服务后重发同一 `clientMsgId` 不会重复插入新消息且返回已有 ID。

## 四、 对标 4：Day One — 私密日记、时间线与情绪回味

### 1. 产品定位与参考范围
- **参考对象**：Day One Journal（iOS/Android 原生设计模式）
- **核心定位**：严肃个人反思、情绪历史组织与私密安全归档。

### 2. 核心功能及交互设计
- **时间线归档**：按月/年垂直分组，时间、情绪图标、第一句正文平铺呈现。
- **事实重于评价**：客观统计打卡天数与文字摘要，不作“你最近表现好/坏”的心理评判。
- **数据物理清除保障**：提供一键彻底销毁数据通道。

### 3. 权威来源依据
- Day One 官方设计指南与数据隐私白皮书（https://dayoneapp.com/guides/）。

### 4. 晚安树洞当前实现状态对比
- **已实现**：
  - `DiaryList.vue`、`DiaryDetail.vue`、`Archive.vue`：纯白背景、无多余卡片、中性阅读排版。
  - `ReportMonth.vue`：白底事实月度报表，仅陈述打卡天数与原话摘要。
  - `DELETE /api/v1/me/data`：受事务锁保护的物理级级联清空机制。

### 5. 值得借鉴的设计
- **克制排版**：16px 字阶、1.75 行距，留白适度，保证深夜暗光阅读舒适度。
- **客观数据呈现**：如实呈现文字，不做虚假的人格评断。

### 6. 不适合照搬的设计
- 不引入复杂的富文本排版（避免 markdown 代码块、多栏布局增加夜间认知负荷）。

### 7. 技术实现方案
- PostgreSQL `Diary`、`LifeJourney` 模型权威存储；个人归档通过 `listUserPublicPosts` 下推 SQL 过滤。

### 8. 成本、性能与维护风险
- 单表存储开销微小，数据生命周期受严格保障。

### 9. 隐私与安全风险
- 个人私密日记绝不向任何第三方公开，跨用户访问强制 404。

### 10. 详细验收测试方法（L1-L5）
- **L2**：用户 A 无法读取用户 B 的日记；调用 `DELETE /me/data` 后所有日记、信件、收藏完全物理清空。

| **CR-5 状态保存与恢复** | 应用在后台被系统杀死恢复后，能够还原关键输入草稿与状态 | 页面编辑草稿持久化存储于本地缓存，重进时无损恢复 |
| **CR-6 网络容错** | 弱网或断网时不可白屏崩溃，具备优雅的错误横幅与重试按钮 | 全量接入 `LoadErrorBanner.vue`，具备友好的中文提示与一键重试 |

## 七、 专项对标：WebRTC 实时通信与 IP 隐私泄露防御

### 1. 核心安全风险揭露（reviewer-glm 重点反证项）
在匿名情绪社交产品中，**绝不允许直接建立未经中继的 P2P 直连 WebRTC 媒体流**！
- **原因**：传统的 P2P WebRTC 在进行 ICE 协商时，双方会交换包含本机真实公网 IP 和局域网 IP 的 `candidate` 信息。对于心怀不轨的恶意用户，只需发起一次语音呼叫，即可通过网络抓包获取对方的真实地理位置（精确到城市甚至家庭宽带运营商网段），彻底击穿匿名保护！
- **权威规范要求**：
  1. 必须强制使用 **TURN Relay-Only 模式**（禁用 Host/Server-Reflexive 直连 candidate），所有音视频流量必须经由可信服务端中继转发，两端之间彻底隔离 IP。
  2. 通话端点必须具备明确的机器可读能力标识（如 `capabilities.call === false`）。在 TURN 服务器凭据与双端真实硬件未就绪前，严格执行 HTTP 501 `Not Implemented` 阻断，前端完全隐藏假通话界面。
