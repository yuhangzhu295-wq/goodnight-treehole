## Earlier rejection findings and measurement boundary

1. **Cross-instance FK clearing is fixed, not waived.** `apps/api/src/relational-runtime.mapper.ts` uses separate `create` and `update` mappings; create may use null for an absent candidate, while update omits `undefined` and thus cannot clear a committed FK. Explicit null and valid referenced strings remain operative. Test 8 at `tests/business/batch1-multi-instance.spec.ts` covers all three for Mood. The reported mutation reverting omission handling failed on the preserved Journey ID. This closes the explicit design obligation at this boundary; it is not proof that all legacy business fields or all models are independently multi-instance safe.
2. **Race proof remains blocked, despite stronger hooks.** `tests/business/batch1-multi-instance.spec.ts` test 4 sets `archiveStarted`/`attemptStarted` before invoking archive/creation; the other side can leave its hook before the operation obtains a lock. All four new barriers time out after 150 ms and never assert the rendezvous completed, so the spec can pass without the claimed overlap. In test 5 `apps/api/src/follow-up-worker.service.ts` calls its notification hook after the claim transaction and before an autocommit insert, while `apps/api/src/batch1-persistence.service.ts` calls the read hook before an autocommit update. Neither holds a lock at the barrier. Test 6 has real hook locations inside the respective transactions (user lock and root lock), but its flags and deadlines do not certify both hooks were entered during the same window. Test 7's pre-commit hook waits for reload, but a timeout lets it commit before the reload begins. The reported `upsert({status:'unread'})` and unconditional-sweep mutations show useful outcome sensitivity; they do not establish the asserted concurrent schedule. This is an within-batch proof gap, not a request to test all schedules or migrate the remaining models.
3. **Benchmark scope remains internally contradictory, although the §2.2 qualification is honest.** `artifacts/persistence-benchmark-after-results.json` retains five samples per mode and scale. At 12,607 rows the reported synchronous Journey p50 comparison is **33,692.0 → 11.5 ms** and the recorded Mode B window **73,811.4 → 186.1 ms**. `scripts/persistence-benchmark-after.ts` now calls `store.drainPendingAiCompletions()` within Mode B, and `apps/api/src/store.service.ts` tracks completion promises. Nonetheless the retained 21-statement trace has no demonstrated callback Snapshot/Journey updates. The specific limitation in `docs/architecture/BATCH1_BENCHMARK_AFTER.md` §2.2 correctly says the 186.1 ms figure is **not** a fully drained end-to-end lifecycle for that operation. Its methodology §1.2 still defines Mode B as fully drained, and its §7 says the **end-to-end lifecycle** improved 396.6×/433.2×. Those unqualified claims contradict §2.2 and the retained trace. The documented exception does not make the article's headline lifecycle conclusion true; either remove that conclusion and relabel Mode B as its measured window, or provide a trace showing callback writes within the window. Worker p50 improvements are **2.2×/4.0×**, not a full-flush-sized gain; database-backed reads are slower by roughly **1.3–6.0 ms** in the sampled comparisons. Worker statement flatness does not erase legacy full-scan read volume.
4. **Baseline identity remains qualified, not newly blocked.** The CI comparator can detect new failing identities when run after a complete suite report; it does not prove that its input covers the full suite. The targeted runner overwrites that report. The provided full-suite identity comparison remains reported evidence only, while the two independently rerun targeted specs establish the central closure. The remaining full-suite failures are baseline/external rather than new Batch 1 regressions on the supplied record. This caveat alone is not a rejection ground.
