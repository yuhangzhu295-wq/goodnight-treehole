## Four earlier blockers, reassessed

1. **Multi-instance proof: strengthened with concurrent barriers across both interleavings.** `two-instance-harness.ts` creates two independent applications and an independent reader. Test 1 executes competing Journey field updates; test 2 races user confirmation against AI completion; test 3 races competing terminal check-ins; AIJob tests 9–10 cover boot non-interference and two-instance terminal CAS. The four previously sequential/uncontrolled tests in `batch1-multi-instance.spec.ts` are now strengthened with explicit mid-operation barriers: Test 4 synchronizes SafetyEvent creation overlapping in-flight archive/detach across both interleavings; Test 5 synchronizes worker delivery retry overlapping mark-read; Test 6 controls concurrent lock acquisition between migrated writes and legacy flush with zero deadlocks; Test 7 synchronizes store reload during an open commit window before commit. All 8 multi-instance tests pass in fresh leased databases, and mutation testing confirms that removing synchronization or protections causes predictable failure.
2. **Stale FK: resolved.** The earlier gate noted that Test 8 reproduced nulling of a valid database `Mood.journeyId` after another instance flushes a stale, field-omitting snapshot, and that 11 other legacy models (`Post`, `Diary`, `PeerExperience`, `PeerMatch`, `DecisionRecord`, `RealityHandoff`, `MessageToFutureSelf`, `PersonalSupportPlan`, `MemoryItem`, `RecoverySnapshot`, and `AgentDecisionLog` — exactly 12 models in total, with `FollowUpJob` as the 13th model having a distinct existing-row preservation path) were exposed by that mapping pattern. This is now fully resolved: `relational-runtime.mapper.ts` distinguishes omission (`undefined`, which omits the field from update so committed database foreign keys survive) from explicit detach (`null`) across all 12 legacy models and for all guarded foreign keys (`journeyId`, `aiJobId`, `commitmentId`, `decisionId`, `letterId`, `moodId`, `peerExperienceId`, `sourceMoodId`). Test 8 in `batch1-multi-instance.spec.ts` empirically proves that committed foreign keys survive stale flushes, and mutation testing confirms that reverting omission handling fails.
3. **Latency comparison: corrected, with explicit Mode B scope qualification.** The artifacts identify the pre-migration commit `5de2d0e`, use the same operations/scales and five samples, and distinguish synchronous Mode A from drained Mode B. At 12,607 rows, the documented `createJourney` p50s match the artifacts: Mode A 33,692.0 ms versus 11.5 ms; Mode B 73,811.4 ms versus 186.1 ms. The old `deliverFollowUp` path has 53 statements, not ~12,694; its measured 2.2x/4.0x large-scale p50 improvements and the slower DB-backed read paths are disclosed accurately. The AFTER worker's `[75,48,48,48,48]` first-sample outlier contains 27 additional `SELECT 1` events in the retained traces. In AFTER Mode B `createJourney`, `BATCH1_BENCHMARK_AFTER.md` now explicitly qualifies the measured 21-statement / 186.1 ms window: it captures the synchronous request plus AIJob submission and terminal CAS execution, while noting that the asynchronous completion callback was previously unawaited by `flush()` alone; the codebase now adds `store.drainPendingAiCompletions()` to close this lifecycle tracking gap. The sample array quotations in §2.2 have also been synchronized with the artifact tables.
4. **CI failing-set identity: substantially closed, with a scope caveat.** `check-baseline-failures.ts` parses the recorded baseline and compares failing file/test names; its five unit tests pass, including a new failure in a previously failing file and a synthetic new spec failure. `ci.yml` runs the comparator after the allowed-to-fail full suite, and the comparator exits 1 on a new recorded identity. This reviewer ran `pnpm check:baseline-diff` after a **targeted** rerun: it returned SUCCESS with zero failures because the runner overwrites `artifacts/runtime/suite-report.json` with the latest run. Thus that invocation does *not* corroborate the orchestrator's earlier full-suite 8-failure comparison. The comparator does not validate `totalFiles`/`fileResults` against the intended suite or fail on an incomplete report with no failure entries (e.g. a file-level execution error). CI's normal full-suite step supplies the appropriate report when completed, but its known-baseline success must be conditioned on that report actually representing the full suite. The reported full-suite identity check is treated as reported evidence, not independently rerun here.
