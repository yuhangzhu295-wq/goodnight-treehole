## Earlier rejection findings and remaining blocker

1. **FK preservation is repaired in code, but the benchmark contradicts it.** `apps/api/src/relational-runtime.mapper.ts` distinguishes create mapping from updates: missing/stale `journeyId` on an existing legacy row is omitted rather than translated into null, while explicit null and valid referenced strings take effect. `tests/business/batch1-multi-instance.spec.ts` test 8 passed on an isolated DB at this HEAD. The reported omission-regression mutation failed as expected. However `docs/architecture/BATCH1_BENCHMARK_AFTER.md` §5 row 4 says that test 8 confirms silent nulling for the unmigrated models, and §7 item 1 repeats that stale flushes overwrite their FKs. Those assertions now conflict with the implementation and the test, and make the batch's declared boundary factually misleading. Correct those claims without claiming that all 35 legacy models are multi-instance safe.
2. **Strict barriers now fail on missing arrivals.** `StrictBarrier.enter` rejects after 2,500 ms, and tests 4–7 await the operations and call `assertAllArrived`; missing a hook fails the test instead of releasing it silently. Test 4's first hook is after SafetyEvent insert and its archive hook precedes locks; its second pairs held Journey lock with the creation's pre-insert hook. Test 6's legacy hook follows admin upserts inside the transaction, and its migrated hook precedes commit inside the other transaction. Test 7 uses two rendezvous to put the reload between an open pre-commit window and its release. These prove selected concurrent windows, not every possible schedule. Tests 1–3 only launch concurrent operations and assert final state; do not advertise deterministic barrier coverage for them.
3. **Notification contention is still unproved.** `apps/api/src/batch1-persistence.service.ts` `markNotificationRead` enters an interactive transaction, reads the row, executes `SELECT ... FOR UPDATE`, invokes `_onInTransaction`, then conditionally updates it. `apps/api/src/follow-up-worker.service.ts` enters its notification transaction, invokes `_onBeforeNotificationWrite` **before any notification SQL in that transaction**, then executes `createMany({ skipDuplicates: true })` for the already-existing notification. The barrier therefore proves overlapping *transaction lifetimes*, with one row lock held, but not two operations contending for that row lock: an insert of a duplicate with `ON CONFLICT DO NOTHING` need not wait on an existing row's non-key update. Removing the worker's transaction wrapper while retaining the same idempotent insert would not be detected by the test's final-state assertions. The reported `upsert({ status: 'unread' })` mutation failure shows that the test detects a status-clobbering writer, not that the normal idempotent retry waited on the mark-read lock. Make the claim precise and supply a test that proves the specific contention if that is the required acceptance assertion; do not equate hook arrival with lock contention.
4. **Benchmark latency scope is now candid.** `docs/architecture/BATCH1_BENCHMARK_AFTER.md` §1.2, §2.2, the 186.1/172.8 ms footnote, §7's measured-window conclusion, and §7's explicit non-proof distinguish the AI-triggering Mode B request-plus-AIJob window from a fully drained completion callback. Non-AI operations can be described as drained. The `end-to-end` worker phrase describes the currently *unproven* O(1) I/O property, not an end-to-end AI latency claim. The measured-window repair closes the previous Mode B wording blocker. Supplied worker speedups remain 2.2×/4.0×, and the sampled DB-backed reads have additional overhead.
5. **Baseline and mutation provenance remain qualified.** The full-suite comparison, typecheck, lint, and three reported mutation failures were supplied rather than independently reproduced in this review. The 19 independently rerun targeted tests pass. The comparator checks failing identities in whichever report is currently at `artifacts/runtime/suite-report.json`; it does not infer full-suite coverage. This limitation alone does not block the batch.

## Scope and user-experience gate

The 35 unmigrated models and FollowUpJob process-local graduation read still prevent application-wide multi-instance safety. AIProvider historical-job deletion guard, AuditLog retention discontinuity, local-clock dependence of the five-minute AIJob recovery threshold, and D/E reviewer-model distinction remain disclosed limitations. Live AI is `AI_LIVE_BLOCKED_EXTERNAL` without a key. No observed pet-presence acceptance session shows that a user feels the pet is real; this persistence gate neither grants nor requires that separate product-experience acceptance. **Blocking here is confined to the unsupported same-row notification contention assertion and the benchmark's contradictory stale-FK assertion.**
